# Product Requirements Document — SlopMachine

## 1. Product definition

**SlopMachine** is a Manifest V3 Chrome extension that helps people review and improve outbound writing before they send it. It detects formulaic, vague, or unpersonalized patterns locally, shows a live **Draft Quality Risk** score in the toolbar badge, and offers reviewable rewrite suggestions in Chrome's Side Panel.

The product is deliberately **backendless**. There is no SlopMachine API, account system, server-side analytics pipeline, or vendor-operated model proxy. Draft text is processed only:

1. by deterministic rules running in the extension;
2. by Chrome's on-device AI, when it is supported and the user enables it; or
3. by a model endpoint the user configures directly — either a local endpoint (for example Ollama or LM Studio) or a remote provider using the user's own API key (BYOK).

SlopMachine is an editorial assistant, not an AI detector, compliance product, deliverability guarantee, or CRM analytics product. A high score means *the draft has signals worth reviewing*, not that its author used AI.

### Product principles

- **Local first:** Continuous analysis never leaves the browser.
- **User-controlled inference:** No rewrite request is made until the user chooses a provider and presses a rewrite action.
- **Review before change:** Never send, auto-send, disable send controls, or replace a draft without a clear user action and a preview.
- **Least privilege:** Ask for site and network access only when a user enables the related integration.
- **Useful without an LLM:** The rule engine, explanations, manual edits, and copy actions work with no provider configured.
- **No invisible telemetry:** No content, scores, URLs, API keys, identifiers, usage events, or analytics are transmitted by SlopMachine.

## 2. Problem and target user

Outbound sellers often paste an LLM draft into Gmail, LinkedIn, or a CRM and send it without adapting its voice or validating placeholders. The result can be vague, over-produced, impersonal, or factually risky.

The primary user is an individual SDR, AE, founder, recruiter, or customer-facing operator who writes outbound messages in the browser. They want a fast, private second pass without changing their email/CRM workflow.

### Jobs to be done

| Job | Desired outcome |
| --- | --- |
| Review a draft while writing | See whether a draft contains concrete, explainable issues without opening another tool. |
| Improve wording privately | Get a useful rewrite from a local/on-device model or the user's own provider account. |
| Keep control of the message | Compare a proposed edit, apply it once, undo it natively, or copy it instead. |
| Avoid accidental sensitive-data transfer | Know exactly when text stays local and when it is sent directly to a selected provider. |

## 3. Scope

### Supported editors

SlopMachine supports Gmail, Outlook Web, HubSpot, Salesforce, LinkedIn, Slack, Google Docs, and common blog CMS editors. Each supported surface has a dedicated adapter so editor discovery, local analysis, issue highlighting, edit application, and native undo are dependable.

### Generic text fields

For most sites opened in Chrome, SlopMachine also supports plain `<textarea>`, text inputs, and standard `contenteditable` fields. Local scoring will usually work; when a site uses a custom editor that cannot safely accept an injected edit, **Apply suggestion** falls back to **Copy** rather than attempting a broad DOM mutation.

### MVP (in scope)

- Dedicated adapters are delivered one at a time, starting with Gmail and LinkedIn, then Outlook Web, HubSpot, Salesforce, Slack, Google Docs, and selected blog CMS editors.
- Generic editable-field support is available as a best-effort, opt-in mode.
- On-device deterministic analysis of the currently focused draft.
- Per-tab toolbar badge and a Chrome Side Panel with score explanation.
- Rule-based transformations that never call a model.
- Optional rewriting through Chrome Built-in AI, a user-configured local OpenAI-compatible endpoint, or a direct remote BYOK provider from a small, explicit provider catalog.
- Preview, apply, native undo where the host editor permits it, and copy-to-clipboard fallback.
- Local-only settings, custom phrase lists, and export/delete controls.

### Explicitly out of scope

- SlopMachine-operated backend, authentication, cloud sync, subscriptions, seat management, or server-side key storage.
- Team leaderboard, manager dashboards, cross-user telemetry, reply-rate attribution, or A/B testing. These require a backend and must not be implied by this product.
- Blocking, intercepting, or sending messages; changing a host product's send button; scraping contacts or CRM records.
- Claiming to determine whether text was generated by AI, guaranteeing deliverability, or fact-checking web claims.
- Mobile Chrome and non-Chromium browsers for the initial release.

## 4. Core experience


### Typical flow

1. The user focuses a supported compose editor and types or pastes at least 25 words.
2. After a 200 ms debounce, the content script analyzes the focused editor locally. The toolbar badge shows 0–100, or is empty when no eligible editor is focused.
3. The user opens the Side Panel for a readable breakdown. No model request occurs merely by opening it.
4. They select an entirely local quick fix or choose **Rewrite**. For an off-device BYOK provider, a disclosure identifies the provider, base URL, model, and the exact text scope about to leave Chrome; the user confirms for that request or enables a remembered per-provider preference.
5. A red/green diff is shown. The user can Apply, Copy, or discard. Apply is one explicit action and preserves host undo behaviour where technically possible.

## 5. Functional requirements

### 5.1 Editor discovery and lifecycle

- Detect the active, focused `<textarea>`, non-password text `<input>`, and `contenteditable` element. Never inspect password inputs, browser-native form fields, or elements marked `autocomplete="cc-*"`.
- Treat only the focused editor as the active draft. Do not scan all text on the page or hidden DOM content.
- Extract plain text with `value` for form controls and `innerText`/selection-aware extraction for rich-text editors. Preserve the host editor's rich formatting; the MVP analyzes plain text only.
- Listen for `focusin`, `focusout`, `input`, `paste`, composition events, and relevant DOM mutations. Debounce input by 200 ms; wait for `compositionend` for IME text.
- Use named platform adapters for Gmail, Outlook Web, HubSpot, Salesforce, LinkedIn, Slack, Google Docs, and selected blog CMS editors, plus a conservative generic adapter. An adapter identifies the actual editor and the safest insertion strategy; it must not rely on a brittle global selector.
- On SPA navigation, editor replacement, tab change, or focus loss, clear stale badge state. The Side Panel must request a fresh snapshot rather than rendering old draft text.
- Initial release does not read cross-origin iframes. If an editor resides in one, show “This editor is not supported yet” rather than attempting to bypass it.

### 5.2 Local Draft Quality Risk analysis

The score is a transparent heuristic from 0–100. It is not an AI-authorship probability. The panel labels it **Low review need (0–30)**, **Review suggested (31–70)**, or **High review need (71–100)**.

| Signal family | Maximum contribution | Examples | User-facing explanation |
| --- | ---: | --- | --- |
| Placeholder and template residue | 35 | `{{first_name}}`, `[Company]`, `INSERT NEWS`, unreplaced merge tags | “This looks like an unfinished template.” |
| Generic/cliché wording | 25 | configurable phrase dictionary, stacked vague claims, empty superlatives | “This phrase may sound generic; consider a concrete example.” |
| Specificity and clarity gaps | 20 | unsupported numeric claim, no subject/object in opening, vague CTA | “The claimed result has no source or concrete context.” |
| Structure and readability | 10 | repeated sentence openings, dense wall of text, excessive bullets | “Several adjacent sentences use the same rhythm.” |
| Paste/edit indicator | 10 | one large paste followed by no material edits during this editor session | “Large unedited paste; review it before sending.” |

Requirements:

- The engine must return a deterministic list of issues with stable IDs, severity, character offsets in extracted plain text, a short explanation, and a safe local suggestion when one exists.
- The score must be capped at 100, explainable as the sum of issue contributions, and recalculated from current text — never from prior tab contents.
- Do not claim a phrase is “used by bots” or invent prevalence statistics. Phrase explanations are editorial guidance.
- Preserve case-insensitive matching, word boundaries, and exclusions for quoted text/code where practical. A user may mute a rule or add an item to an allow-list.
- Do not store raw draft text in persistent storage. Per-editor in-memory text is discarded on navigation/unload. `chrome.storage.session` may hold only the current score, issue summaries, and a short-lived revision token needed to hydrate the panel; clear it when the tab closes.

### 5.3 Toolbar badge and non-blocking feedback

- Use `chrome.action.setBadgeText`, `setBadgeBackgroundColor`, and `setTitle`, scoped to `sender.tab.id`.
- Show the integer score only for eligible focused drafts of at least 25 words. Otherwise clear the badge text and title state.
- Badge colors: green `#10B981` (0–30), amber `#F59E0B` (31–70), red `#EF4444` (71–100). All score meaning must also be available as text; color is never the only signal.
- Action title example: `SlopMachine: review suggested (48/100)`. Unsupported sites use `SlopMachine: no supported editor focused`.
- An optional editor outline may be enabled in Settings; it is off by default, does not alter layout, and is never a send blocker. There is no floating widget in MVP.

### 5.4 Side Panel

Clicking the extension action opens the extension Side Panel. No action popup is declared. The panel is tab-aware and must render one of these states: no supported editor, draft ready, analyzing, provider unavailable, rewrite in progress, output ready, or stale draft changed.

The draft-ready view contains:

- Score, textual status, word count, estimated reading time, and “last analyzed” state.
- An issue list ordered by severity. Each item includes highlighted snippet, category, rationale, confidence-free wording, and dismiss/mute action.
- Local actions: remove/rewrite a cliché, remove an empty opener, shorten a selected passage, or copy a suggested revision. They must work with no AI provider.
- Rewrite controls: target tone (direct, concise, conversational), length (shorter/same), and a **preserve facts** toggle enabled by default.
- A diff preview that is keyboard accessible. It shows the original and proposed text, all substantial changes, the model/provider used, and any provider warning.
- Apply, Copy clean text, and Discard. Apply is disabled when the focused editor changed after generation; the panel offers Regenerate instead.

The panel must not show a raw draft after the source editor loses focus or closes unless the user has explicitly copied it. This avoids leaving sensitive content visible in a persistent side panel.

### 5.5 Applying an edit safely

- Before applying, compare the analysis revision token with a freshly requested editor token. If it differs, reject the operation with “Your draft changed — review or regenerate.”
- Prefer selection replacement using the adapter and a real `InputEvent`/host-supported editing path. For plain controls, use `setRangeText` where suitable; for contenteditables, use selection/range insertion or the host adapter. `document.execCommand` is a last-resort compatibility path, not the primary contract.
- Dispatch the events expected by the host editor and verify the visible plain text after replacement. If verification fails, restore the prior selection where possible and offer Copy instead.
- Native `Cmd/Ctrl+Z` is a best-effort integration requirement, not a guarantee across React/Draft/Lexical editors. Acceptance testing must verify it for every supported adapter.
- Never modify a draft in response to analysis, opening the panel, receiving model output, or page navigation.

### 5.6 Rewrite providers and routing

Provider selection is explicit and per user. The Settings screen shows availability, privacy boundary, endpoint, selected model, and storage mode.

| Priority | Provider | Data path | Required behaviour |
| ---: | --- | --- | --- |
| 1 | Chrome Built-in AI | Chrome-managed on-device model | Check `LanguageModel.availability()` from an extension document, handle `available`, `downloadable`, `downloading`, and `unavailable`, and create only after a user gesture when required. |
| 2 | Local LLM | Browser → user’s `http://localhost`/`127.0.0.1` endpoint | Support OpenAI-compatible chat-completions first; endpoint and model are user-configured; key is optional. Connection tests send a non-sensitive fixed probe, never a draft. |
| 3 | Remote BYOK | Browser → catalogued provider endpoint directly | Begin with OpenAI-compatible providers whose exact HTTPS origin is declared in the manifest. The user selects a provider/model and supplies a key; requests go directly to that provider, never through SlopMachine. |
| 4 | No model | No request | Keep local analysis and rule-based actions available. |

Rules for every provider:

- Model calls occur from the Side Panel (an extension document), not the service worker. Chrome's current Prompt API is not available in Web Workers.
- Never silently fall back from on-device/local to a remote provider. The user selects or confirms the fallback.
- Use a versioned, bounded prompt template that treats draft text as untrusted data. It must prohibit adding facts, citations, metrics, names, URLs, or claims not already supplied by the user, and request a plain-text rewrite only.
- Render output as text, never HTML. Strip control characters, cap output length, and show a warning that generated copy needs review.
- Set request timeouts, support cancellation with `AbortController`, and expose clear provider errors without including the draft or API key in logs.
- Do not make automatic model retries that could repeat a sensitive-data transfer.

### 5.7 Settings and configuration

Settings include:

- Site enablement toggles, experimental generic-editor toggle, minimum word threshold, optional outline, phrase allow-list, custom flagged phrases, and reset-to-defaults.
- Provider add/remove; active-provider selector; connection test; model name; local endpoint; and “do not persist key” (default) or “persist locally on this device” acknowledgement. Remote provider endpoints are fixed by the reviewed catalog in MVP.
- Data controls: clear all local settings, clear current session analysis, and export/import **rules and settings only**. Export never contains draft text or secrets.
- Provider access can be revoked by deleting its configuration; remove the associated optional host permission if no configured provider uses that origin.

## 6. Privacy and security requirements

### Data policy

| Data | Default handling | Retention |
| --- | --- | --- |
| Draft text | In content-script memory; optionally sent only by the user to their selected provider | Discard on editor/tab lifecycle; never persist in extension storage |
| Scores and issue summaries | Session-only state for badge/panel | Cleared on tab close/session end |
| Rules and UI preferences | `chrome.storage.local` | Until user changes/clears them |
| API keys | Memory-only by default | Cleared when extension/browser session ends; persistence is opt-in and clearly warned |
| Local model URL / remote endpoint / model ID | Local settings | Until user removes it |

`chrome.storage.local` is not a hardware keychain and must not be described as encrypted secret storage. The product should recommend memory-only keys; persistent storage is an informed user trade-off. Never place a key in the manifest, source code, URL query, analytics, console output, exported settings, error reporting, or clipboard.

### Consent and disclosure

- On first remote rewrite, show a one-time, provider-specific disclosure: “This sends the selected draft text directly to **{provider name}** at **{origin}** using your key. SlopMachine does not receive it.” Include Cancel and Continue.
- A separate confirmation is required if the endpoint origin, provider type, or key configuration changes.
- The endpoint test must use a static non-sensitive probe and reveal its exact endpoint before requesting optional host access.
- Extension code may not use remote-hosted executable code. Content Security Policy must disallow arbitrary remote scripts/eval.
- No third-party analytics, trackers, crash reporter, fonts, or remotely hosted assets in the extension bundle.

### Permissions model

Use optional permissions wherever Chrome allows. Initial installation requests only the permissions needed for local functionality:

```json
{
  "manifest_version": 3,
  "name": "SlopMachine",
  "version": "0.1.0",
  "description": "Private, local-first review for browser-based outbound drafts.",
  "permissions": ["sidePanel", "storage", "scripting"],
  "optional_host_permissions": [
    "https://mail.google.com/*",
    "https://*.linkedin.com/*",
    "https://api.openai.com/*",
    "http://localhost/*",
    "http://127.0.0.1/*"
  ],
  "background": { "service_worker": "service-worker.js", "type": "module" },
  "action": { "default_title": "SlopMachine" },
  "side_panel": { "default_path": "sidepanel/index.html" },
  "options_page": "options/index.html",
  "content_security_policy": {
    "extension_pages": "script-src 'self'; object-src 'self'"
  }
}
```

The `scripting` permission is used to register the packaged content script only after the user enables a permitted site; do not declare a broad static content-script match. Remote BYOK is limited to a reviewed catalog of exact origins predeclared under `optional_host_permissions` and requested only when that provider is enabled. A Chrome extension cannot add a new exact origin to its manifest at runtime. Arbitrary remote URLs are out of scope for MVP because they require predeclaring a broad host pattern such as `https://*/*`; local endpoints remain configurable within the declared loopback origins. The final manifest must use only permissions verified necessary by implementation; do not include `tabs` pre-emptively.

For a site integration, request the matching optional site permission when the user turns that site on, then register or enable the matching content script. The product must explain why each permission is requested and continue working in settings/no-provider mode if it is denied.

## 7. Technical architecture

### Components

| Component | Responsibilities | Prohibited responsibilities |
| --- | --- | --- |
| Content script | Focused editor discovery, plain-text extraction, local analysis, adapter-driven highlight/apply, short-lived in-page state | Network calls to remote models; scanning the whole page; persistent draft storage |
| Service worker | Badge/title update, tab/session lifecycle, permission orchestration, message routing | Holding model sessions, draft contents, API keys, or network inference |
| Side Panel | Read current analysis, local suggestion UI, consent, provider selection, direct rewrite request, diff/review | Automatically applying or sending edits |
| Options page | Permissions, rules, provider configuration, reset/export controls | Testing with user draft text |
| Shared modules | Rule engine, typed messages, schema validation, diffing, sanitization, provider adapters | Browser-specific DOM mutation |

### Message contracts

All messages are versioned and schema-validated. Avoid generic `any` payloads. A sample minimal contract:

```ts
type AnalysisSnapshot = {
  version: 1;
  tabId: number;
  editorId: string;
  revision: string; // hash/token scoped to the live editor; not persisted with source text
  score: number;
  status: 'low' | 'review' | 'high';
  wordCount: number;
  issues: Array<{ id: string; category: string; severity: 'info' | 'warning' | 'critical'; start: number; end: number; message: string }>;
};
```

The content script remains authoritative for the live editor. The Side Panel must ask it to revalidate immediately before highlighting or applying any proposal.

### Chrome Built-in AI compatibility

Chrome's current API surface is `LanguageModel`, not `ai.languageModel`. Availability and session creation are asynchronous and must be feature-detected. Chrome Built-in AI has hardware/OS/language constraints and may require a model download and meaningful user activation. Therefore it is an optional provider, never a prerequisite or silent fallback. Re-check its documented extension support at release time.

### Reliability and performance

- Local analysis target: p95 under 75 ms for a 1,000-word plain-text draft, excluding the 200 ms debounce.
- Do not block typing, paste, page navigation, or host editor event propagation.
- Cancel in-flight analysis when revision changes; cancel an in-flight model request on user cancel, tab close, or provider switch.
- Cap analyzed input at 12,000 characters in MVP, warn when truncated, and never rewrite truncated text without an explicit user choice.
- Maintain a capability matrix for every site adapter: detection, analysis, highlight, full-editor apply, selection apply, native undo, and copy fallback.

## 8. Acceptance criteria

### Local-only baseline

- With no provider configured and networking disabled, a Gmail/LinkedIn supported editor produces a score and explainable issue list locally.
- Opening the Side Panel makes no network request and does not write draft text to persistent extension storage.
- A 30-word paste containing `{{first_name}}` creates a placeholder issue; replacing it removes that issue on the next debounced analysis.
- Focus loss, tab switch, or unsupported editor clears the badge within 500 ms and prevents stale text from being displayed as current.
- No send button, click handler, or keyboard shortcut in the host application is blocked or modified.

### Provider behavior

- If `LanguageModel` is unavailable/downloadable/downloading, the UI states why and preserves local features.
- A configured local endpoint receives a rewrite only after the user presses Rewrite. Its connection test uses the documented static probe.
- A remote endpoint receives no draft until the user approves the provider-specific disclosure. A rejected disclosure causes no request.
- Switching providers never sends the earlier draft to the new provider automatically.
- API keys are absent from extension application logs, error messages, exported settings, and the visible UI after saving. The user is told that browser developer tools and their selected provider may expose or receive the authorization header as part of a direct request.

### Editing and resilience

- A generated proposal always shows a diff before Apply.
- If the user changes the editor after generation, Apply is disabled and no stale replacement occurs.
- For each supported adapter, integration tests cover: normal typing, paste, IME composition, SPA navigation, open/reply compose, apply, and `Cmd/Ctrl+Z`; unmet undo support must fall back to Copy and be documented in the capability matrix.
- Unsupported editors fail closed with a clear state; they do not attempt broad DOM mutation.

### Accessibility and UX

- Side Panel is fully keyboard navigable with visible focus, semantic labels, non-color status labels, and screen-reader text for score and diffs.
- The disclosure, errors, and no-provider state explain the next action in plain language.
- All functionality works in a narrow Side Panel width and respects light/dark Chrome themes.

## 9. Delivery plan

### Phase 0 — Product safety spike

- Validate Gmail and LinkedIn adapter selectors and replace/undo behavior.
- Prove Side Panel ↔ content-script revision validation.
- Prototype Built-in AI availability in an extension page and a local OpenAI-compatible request to Ollama/LM Studio.
- Complete a permission and data-flow review before any remote BYOK adapter is added.

### Phase 1 — Private local MVP

- Optional Gmail/LinkedIn permissions and content scripts, plus the opt-in generic-editor mode.
- Deterministic rule engine, per-tab badge, Side Panel issue feed, local quick fixes, and Copy fallback.
- Settings, custom rules, data reset, and automated unit/integration tests.

### Phase 2 — Opt-in inference

- Chrome Built-in AI provider with capability/download states.
- Local OpenAI-compatible endpoint configuration, consent-aware direct request, diff preview, cancellation, and error handling.
- Remote HTTPS BYOK provider only after permission/consent tests pass.

### Phase 3 — Supported-editor coverage, not a backend

- Add Outlook Web, HubSpot, Salesforce, Slack, Google Docs, and common blog CMS editors one adapter at a time, each with a capability matrix and dedicated integration tests.
- Consider import/export of non-secret rules and an organization-distributed rules file only if it remains static/local and needs no SlopMachine service.

## 10. Open decisions to resolve before implementation

1. **Remote BYOK provider shortlist:** Start with OpenAI only, or add each compatible provider as an individually reviewed, manifest-declared origin. The MVP recommendation is OpenAI only.
2. **Persistent key policy:** Memory-only is safest; persistent local storage must remain opt-in with an explicit explanation that it is not OS-keychain protection.
3. **Generic editors:** Keep experimental/off by default until the adapter safety model is proven across real sites.
4. **“Human Injection Score” naming:** Do not use it as a truth claim. If retained, rename it to **Edit-after-paste indicator** and show it only as a private, session-local review cue.

## 11. What changed from the previous concept

The live score, toolbar badge, Side Panel diagnosis, and one-click editable suggestions remain the product's center. The requirements now remove the incompatible serverless fallback and enterprise telemetry, define direct BYOK/local/on-device routes, prohibit silent transfer and auto-edits, make key handling honest, and add the permissions, consent, lifecycle, unsupported-editor, provider-failure, and test requirements needed for a shippable privacy-first extension.

### 12.3 Key Interactive Components

1. **The Tactical Gauge HUD (Slop Meter):**
   - A semi-circular SVG arc with animated SVG stroke offset.
   - Live color interpolation: `#10B981` (0-30), `#F59E0B` (31-70), `#EF4444` (71-100).
   - Monospaced numerical readout with `/100` sub-label and animated transition on text update.

2. **Interactive Issue Cards:**
   - Severity tag pill (`CRITICAL`, `WARNING`, `NOTICE`) in monospace.
   - Flagged text snippet shown in a monospaced code-block pill with line/character offset.
   - Quick Action button per card (e.g. *Remove*, *Punch Up*, *Ignore*).
   - Hovering over an issue temporarily pulses a non-destructive highlight outline in the active web editor.

3. **1-Click Tone Chips & Rewrite Studio:**
   - Interactive segmented toggle chips:
     - `⚡ Cut Fat`: Strips filler, reduces word count by 35-50%, eliminates corporate preambles.
     - `🎯 Direct Executive`: Formats text into 2-sentence maximums, bullet points, and an explicit CTA.
     - `🤝 Conversational Peer`: Replaces formal boardroom language with natural founder-to-founder dialogue.
   - **Strict Fact Lock Toggle**: Injects constraints into the prompt forbidding the model from adding new claims, metrics, or company names not already in the draft.

4. **Split / Unified Diff Viewer:**
   - Visual red strike-through (`background: rgba(239, 68, 68, 0.15); color: #FCA5A5`) for removals.
   - Visual green highlight (`background: rgba(16, 185, 129, 0.15); color: #6EE7B7`) for additions.
   - Token streaming state: Blinking cursor indicator while the model streams output.

## 13. Zero-Backend Inference Contracts & Provider Implementation

Because SlopMachine operates strictly with **no backend servers**, all inference is routed directly from the extension Side Panel to the selected engine.

### 13.1 Provider 1: Chrome Built-in AI (`window.ai` / `LanguageModel`)
- **Prerequisites:** Chrome 128+ with Prompt API enabled (`chrome://flags/#prompt-api-for-gemini-nano`).
- **Data Path:** 100% on-device Gemini Nano. Zero bytes transmitted over network.
- **Implementation Contract:**
  ```javascript
  // sidepanel/providers/chrome-nano.js
  export async function checkChromeAIAvailability() {
    if (!('ai' in self) || !('languageModel' in self.ai)) return 'unavailable';
    const capabilities = await self.ai.languageModel.capabilities();
    return capabilities.available; // 'readily' | 'after-download' | 'no'
  }

  export async function streamChromeAIRewrite(draftText, preset, onChunk, signal) {
    const session = await self.ai.languageModel.create({
      systemPrompt: "You are an expert editor who strips AI clichés and corporate fluff from sales emails. Output ONLY the rewritten email in plain text with no commentary."
    });
    const prompt = buildEditorialPrompt(draftText, preset);
    const stream = session.promptStreaming(prompt, { signal });
    for await (const chunk of stream) {
      onChunk(chunk);
    }
  }
  ```

### 13.2 Provider 2: Localhost LLM (Ollama / LM Studio)
- **Target URL:** `http://localhost:11434/api/generate` (Ollama) or `http://localhost:1234/v1/chat/completions` (LM Studio).
- **Security & CORS:** Requires no API key. The documentation guides technical users to launch Ollama with extension origin support:
  `OLLAMA_ORIGINS="chrome-extension://*" ollama serve`
- **Streaming Implementation:** Uses standard `fetch` with `ReadableStream` reader and `AbortController`.

### 13.3 Provider 3: Direct Remote BYOK (Bring Your Own Key)
- **Supported Providers:** OpenAI (`https://api.openai.com/v1/chat/completions`), Anthropic, Groq (`https://api.groq.com/openai/v1/chat/completions`), OpenRouter.
- **Key Storage Contract:**
  - Default: Kept in **memory only** (in-memory variable in sidepanel document, discarded on panel close).
  - Optional: User clicks "Remember on this device" -> stored in `chrome.storage.local`. Explicit warning provided that local storage is accessible by device administrators and is not hardware-encrypted.
- **Strict Headers:** `Authorization: Bearer ${userKey}`, `Content-Type: application/json`. No custom tracking headers.

### 13.4 Strict Editorial System Prompt & Temperature Calibration
To prevent the model from outputting more "AI Slop", the system prompt enforces strict journalistic brevity:
```
System: You are an uncompromising editorial assistant. Your job is to make outbound email sound human, direct, and unpretentious.
Rules:
1. NEVER use the words: "delve", "testament", "spearhead", "tapestry", "elevate", "foster", "synergies", "game-changer", "streamline".
2. NEVER add introductory pleasantries ("Hope you are well", "I know you are busy").
3. NEVER invent facts, metrics, logos, or client names.
4. Keep sentences under 15 words where possible.
5. Return ONLY the edited text. No conversational filler, no quotes around the output.
```
